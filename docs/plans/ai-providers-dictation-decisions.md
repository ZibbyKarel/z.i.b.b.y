| A5  | **The approval gate must hold for opencode runs.** Preferred: an opencode plugin/hook that calls the same gate decision as `claude-approval-hook.mjs` before each tool call. | A6  | System prompt + MCP servers reach opencode per run through env `OPENCODE_CONFIG_CONTENT` (an ad-hoc agent + `--agent`), never by writing into the operator's `~/.config/opencode`                                                                    | Per-run, no shared mutable state, parallel runs cannot clash                                                                                |

| A13 | Gate for opencode = three layers: run config with `ask` for everything and **no `--auto`**; `deny` rules for `execute` (Code Mode), `question` and every tool missing from the agent's `tools` allow-list; a default-deny plugin that runs `claude-approval-hook.mjs` per tool call. Supersedes the `OPENCODE_CONFIG_CONTENT` idea in A6: the config is a 0600 file in `<runsDir>/.opencode/`, outside the agent's free zone, persisted in the run spec and rewritten before every spawn | Review proved a bypass through `execute` + `session_move`, and that a config inside the sandbox can be rewritten before a resume; env would leak MCP secrets to the agent's shell |
| A14 | `free` = provider `opencode` **and** an all-zero price list in opencode's model catalog; unknown = not free                                                                                                                                             | A zero cost in usage history also matches paid subscriptions (ChatGPT sign-in); D0c makes a wrong "free" label a real defect                |
| A15 | Changing `aiEngine` / `opencodeModel` or an agent's `engine` / `engineModel` needs the operator token (field-level 401); other settings saves are unchanged                                                                                          | An agent must not be able to move itself or another agent to a different engine or a paid model (Law 4)                                     |
| A16 | Claude's 5h / weekly windows never pause or defer an opencode run, stage or task with a known opencode target; opencode runs get an idle watchdog (`ZIBBY_OPENCODE_IDLE_MINUTES`, default 10)                                                         | Otherwise switching to opencode when Claude is exhausted would still run nothing; opencode occasionally hangs silently                      |
| A17 | With a global opencode engine the orchestrator is not pinned to Claude; it runs without the `--agents` catalog (delegation falls to opencode's own subagent, still gated)                                                                             | Pinning would silently keep spending Claude after the operator switched away                                                                |
| A18 | **Supersedes A1's "why"** (2026-11-12, opencode 2.2.7). Claude can now run through opencode's built-in **Claude Agent** provider (`claude-agent/*`), which drives the installed `claude` via the Claude Agent SDK on the operator's Claude Code login. The native `claude` engine stays the default. A `claude-agent/*` model spends the Claude subscription, so Claude's 5h / weekly limits apply to it exactly as to the claude engine (one predicate `spendsClaudeSubscription`, used by RunnerCore, agent runs, workflow stages and the task scheduler). The model picker marks it `subscription` (empty catalog price), not `free`. A10 is unchanged: the operator connects it themself with `opencode auth login claude-agent`. The gate was re-proven live on `claude-agent/haiku` | opencode now offers a sanctioned subscription path; A16 would otherwise let a `claude-agent` run ignore an exhausted window it is spending |
| A19 | Stored model aliases become engine-independent **model tiers**: `haiku`=1, `sonnet`=2, `opus`=3, `fable`=4 (`ModelTierSchema` / `MODEL_TIERS` in `libs/contracts`; `AgentModelSchema` and `ChatModelSchema` are that enum, so agents / phases / escalation / advisor gain `fable`). Stored values don't change → no migration. The claude engine passes the tier as `--model` unchanged (the installed `claude` lists `fable` as an alias) | Model choices must not depend on the engine; opencode ignored them before |
| A20 | `SystemConfig.opencodeTierModels: { haiku?, sonnet?, opus?, fable? }` (opencode `provider/model[#variant]`, default `{}`). opencode model = explicit `engineModel` (phase, then agent) → the tier's mapping → nearest mapped lower tier → nearest mapped higher tier → `opencodeModel` → refuse (A7). Tier = `escalation?.model ?? phase.model ?? agent.model`. The pure `resolveTierModel` lives in `libs/contracts` (the web shows the resolved model). `thinking` was ignored on opencode here; superseded by A26 (thinking → `#variant`). Changing a mapping needs the operator token like `opencodeModel` (A15) | An engine with fewer models than tiers never fails, and the Kodér ⇄ Review escalation ladder really escalates on opencode |
| A21 | `WorkflowPhase.engine?` + `WorkflowPhase.engineModel?` (agent phases only; `engineModel` needs `engine: "opencode"`; neither with `openaiModel`). Stage engine = `phase.engine ?? agent.engine ?? SystemConfig.aiEngine`; `phase.engine: "claude"` forces the native CLI. Threaded through stage build, `phaseSpendsClaude`, `preflightEngines` (every escalation rung) and the scheduler's `targetOffClaude`. Workflow create/update whose phases' `engine` / `engineModel` differ from the stored ones (per phase id) needs the operator token (field-level 401). The only other workflow writers (chat self-API: no `phases` key; skill removal: rewrites `phases` it read) can't set them | The operator mixes engines inside one workflow; an agent must not move a step to another engine or a paid model (Law 4) |
| A22 | Stays Claude: the `openaiModel` text stage, the haiku/sonnet one-shots, and the phase advisor. The advisor is a Claude session, so an opencode stage's `ask_advisor` returns "not available" (log line `advisor skipped for opencode stage …`) and sends the agent to `ask_operator` instead of spending Claude behind the operator's engine choice (before, it silently ran a fresh Claude session) | The advisor forks a Claude session; an opencode stage has none, and Claude may be the exhausted engine |
| A23 | **Mechanism superseded by A30 for chat** (the merge below is removed; `readOperatorMcpServers` stays for runs, A27). Chat on the claude engine also mounts the operator's own MCP servers: user scope (`~/.claude.json` → `mcpServers`) plus the `.mcp.json` of every enabled plugin (id `plugin_<plugin>_<server>`, `${CLAUDE_PLUGIN_ROOT}` expanded), read by `readOperatorMcpServers` (`apps/api/src/inventory/operator-mcp-servers.ts`) and written into the turn's 0600 `--mcp-config`. A server disabled for the turn's cwd (`projects[cwd].disabledMcpServers`) is skipped; the reserved ids `zibby` / `zibby-kb` win a name clash. `--setting-sources ""` and the built-in denylist stay. Measured 2026-11-12 (haiku, one turn each, n=1): no servers 7.2 s wall / 935 ms `duration_ms`, operator servers 6.9 s / 1019 ms; init after 2.2 s with the servers mounted. No mitigation needed. Found live: OAuth-backed HTTP servers don't authenticate when passed through `--mcp-config` (claude-design `failed`, context7 `needs-auth`); only playwright (stdio) connected | "Chat is a superstructure over the terminal": the operator's servers, not just claude.ai connectors |
| A24 | **Supersedes A3 for chat.** A chat turn runs on the effective engine: `resolveAiEngine` with the mentioned `@agent`, else the global `aiEngine`. On opencode: `opencode run --standalone --format json -m <model> --agent zibby [--session <id>]`, system prompt as the `zibby` agent in a 0600 `OPENCODE_CONFIG` file (deleted after the turn), model from the tier mapping (an agent's `engineModel` wins; tier = per-turn `model` ?? agent `model` ?? `ZIBBY_CHAT_MODEL`). The transcript stores `sessionEngine`; a stored session from the other engine is not resumed (fresh session, no context carry-over). JSONL → the existing SSE events (text parts arrive whole, joined with a blank line). Unusable opencode → one `error` event with the preflight message (A7). **Deviation from the brief:** the operator's servers (A23) are **not** mounted on opencode — only `zibby` + `zibby-kb` | Live, opencode offered all 25 Playwright tools (incl. `browser_run_code_unsafe`, `browser_file_upload`) and has no auto-mode classifier to stop them; mounting them needs a per-tool allowlist or a gate path first (follow-up) |
| A25 | Tool gating for opencode chat is fail-closed and needs no approval path: config `permissions` = deny `*`, allow `<server>_*` for each mounted server (`zibby_create_task` additionally denied when an `@agent` is mentioned), no `--auto`, plus the `zibby-chat-gate` plugin (`apps/api/src/chat/opencode-chat-gate/index.mjs`) that denies on `permission.evaluate` and throws on `tool.execute.before` for anything that isn't a mounted MCP tool (shell, edit, write, execute, question, skill, subagent, web*, `opencode_*`). claude.ai connectors don't exist on opencode; the system prompt tells the model to say so | The run gate's ask path needs RunnerCore's intent-request watcher and an approval card; chat has neither, so an `ask` would wait a day. Denying is the only safe default (Law 1, Law 4) |
| A26 | On opencode, `thinking` (`escalation?.thinking ?? phase.thinking ?? agent.thinking`) selects the model variant of the same id: when the resolved model has no explicit `#variant` and the catalog (`opencode api GET /api/model`, cached like the engines probe) lists that variant id, the run uses `provider/model#<level>` (`opencode run -m provider/model#variant`, verified on opencode 2.2.7: `opencode stats` records the variant). An explicit `#variant` (engineModel / tier mapping / opencodeModel) wins; no matching variant or an unreadable catalog = run unchanged, never a failure. Recorded `engineModel` includes the variant; the stage log names why thinking did not apply. `GET /ai-providers/engines` model entries gain `variants: string[]` (default `[]`) | The operator wants thinking levels on opencode too; claude-agent and several free models expose effort variants whose ids match the levels |
| A27 | **Runs get the operator's own MCP servers by grant, never by default.** `readOperatorMcpServers` (user scope + enabled plugins, the A23 reader) is a second, read-only source next to the registry with `grantOnly` semantics: an agent / stage / task whose `tools` or `toolGrants` name the id (`<id>`, `mcp__<id>`, `mcp__<id>__…`) gets it mounted on both engines, raw config into the 0600 `--mcp-config` / opencode run config. A registry row with the same id wins (even disabled); `zibby-entities` / `zibby-kb` / `zibby-run` are never taken from the operator; an id the registry would reject or a transport other than stdio/http/sse is skipped. Chosen over "import into the registry": no such import path exists, and a copy would go stale against `~/.claude.json` and duplicate secrets into the credentials store | A prompt-injected run must not get a browser or third-party tools for free (Law 4); reusing the grant path keeps one mechanism |
| A28 | **MCP calls in runs go through the ZibbyOS gate.** Hook matcher `…|mcp__.*`; `classifyMcp` (both engines): ZibbyOS's own three servers → unchanged (exact ids — not a `zibby-` prefix or a loopback URL, fail closed); read-only tool name (read verb as 1st/2nd word, no write word anywhere) → `mcp.read`, new system rule `floor-mcp.read` = **notify**; Never-rule-like names keep their action (`pr.merge`, `payment`, `purchase`, `delete`, `deploy`, `send_email`); everything else and an unparsable name → `mcp.write`, new system rule `floor-mcp.write` = **ask** (human). The MCP branch fails **closed** on a classifier exception. An allowed MCP call exits without a decision so Claude's own permission layer still applies. Hook requests are serialised per run with `intent.lock` (parallel MCP reads / `Task`s overwrote the single request file and stranded a hook for up to 24 h). Autopilot does **not** cover `mcp.write`. A custom PreToolUse hook whose matcher contains `mcp` is dropped like a Bash/Task one | Law 1 + Law 4: before this, MCP calls in runs reached only Claude's auto classifier (and on opencode nothing). Ceiling: classification is by tool name only |
| A28a | **Amendment to A28 (2026-11-12): registry servers keep the pre-A28 behaviour.** Servers the operator registered and enabled in ZibbyOS's own MCP registry (`McpServersStorageService`) and the run mounted are not classified — no `mcp.read`/`mcp.write`, Never-rule-like names included (the hook never saw them before A28). The classification applies to A27 inventory servers and any `mcp__*` tool not positively from the registry (fail closed). The list reaches the hook only as argv[3], baked in by the API (`--settings` hook command on claude; `ZIBBY_MCP_REGISTRY` set over the project env → the opencode gate plugin's spawn argv). Ids compare in tool-name form, exactly. An inventory server whose tool-name id equals or `_`-extends a registry/built-in id (or vice versa) is not mounted (`mcpIdsCollide`), so it can't masquerade. Same amendment: publish CLIs (`npm/pnpm/yarn publish`, `cargo publish`, `gem push`, `twine upload`, `docker/podman push`) → `deploy` (operator decision, same day; card text „Publikovat balíček nebo image do registru“); `kubectl … delete`, `aws … delete-*/terminate-*/remove-*`, `aws s3 rb` → `delete` (never lifted by the ownership ledger); `jira issue create` / `jira create` → `jira.create_issue`; `--dry-run` publishes and `curl -X POST` stay unclassified | A28 parked every Playwright call of `ui-ux-tester` (`web-qa`, `pr-review-browser`) — registering a server is already the operator's trust decision and its grant is per agent. Publishes are `deploy`, not `git.push` (operator): a registry release is a deploy; `deploy` is never autopilot-covered, not branch-scoped, and not a file action the ledger could lift — and moving `floor-git.push` would not silently open publishes |
| A29 | **claude.ai connectors do not load in runs** (verified 2026-11-12, claude 2.1.322, haiku, n=1 each): with `--setting-sources ""` the init event has `mcp_servers: []`; the same command without it lists the connectors (`source: "claudeai"`: Atlassian, Slack, Figma, Claude Data/Docs, …, many `needs-auth`). The fetch itself is gated only on strict MCP config / managed policy / `--bare` in the binary, so the filter is elsewhere — not found. Not changed: re-enabling a setting source would also load the operator's hooks, plugins and settings into every run. opencode can never have them (Claude login) | Isolation is the bigger guarantee; reported as an open item |
| A30 | **Supersedes A23's mechanism for chat.** The Claude chat turn loads the operator's user setup: `--setting-sources user --settings '{"disableAllHooks":true}'`, env `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` + `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` (`CHAT_CLAUDE_SETTINGS` / `CHAT_CLAUDE_ENV` in `chat-session.service.ts`). The built-in denylist, `--permission-mode auto`, the persona and the `zibby` / `zibby-kb` `--mcp-config` stay; the `--mcp-config` no longer carries the operator's servers (they load natively). Verified 2026-11-12, claude 2.1.322, haiku, through the real chat service: init lists 48 servers, connected: plugin playwright, zibby, zibby-kb, claude.ai Claude Data / Docs / Atlassian MCP / Slack / Figma / Atlassian; no hook event in the stream; the model reports no superpowers / graphify / RTK / ponytail / CLAUDE.md / MEMORY.md context; `slack_list_user_channels` (read) returned channels; "postav mi malou todo aplikaci v Reactu" called `create_task` (n=2); the mcp-config file is gone after each turn. Auto-memory was found leaking with only the CLAUDE.md flag, hence the second env flag. Lost: plugins whose tools a hook registers (`helper-desk`, `handoff`). The rest of the user settings (`env`, permission rules, language, output style) comes along too (not checked individually). ### Contract sketch (A)

```ts
// system.schema.ts
aiEngine: z.enum(['claude', 'opencode']).default('claude')
opencodeModel: z.string().default('') // "provider/model"
opencodeTierModels: { haiku?, sonnet?, opus?, fable?: string }.default({}) // A20

// ai-providers.schema.ts (A19/A20)
MODEL_TIERS = ['haiku', 'sonnet', 'opus', 'fable']; ModelTierSchema = z.enum(MODEL_TIERS)
resolveTierModel(tier?, tierModels?, fallback): string

// workflow.schema.ts — WorkflowPhase (A21, agent phases only)
engine: AiEngineSchema.optional()
engineModel: z.string().min(1).optional() // needs engine: 'opencode'

// agent.schema.ts
engine: AiEngineSchema.optional()
engineModel: z.string().optional()

// ai-providers.contract.ts
GET /api/ai-providers/engines ->
  { engines: [
      { id: 'claude', available, version },
      { id: 'opencode', available, version, providers: string[], models: string[] } ] }
GET /api/ai-providers/usage?days=30 ->
  { opencode: { available, totals: Usage, models: [{ providerId, modelId, ...Usage }] } }
// Usage = { steps, costUsd, tokens: { input, output, reasoning, cacheRead, cacheWrite } }
```

## B — Czech dictation

| #   | Decision                                                                                                                                                                                                 | Why                                                                                                                         |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| B1  | Root cause of the earlier failures: Web Speech API needs Google's cloud service, which Electron does not have (`network` error), and the packaged app has no `NSMicrophoneUsageDescription` / permission handler | Found in `apps/desktop` (no mic wiring at all) and `useSpeechRecognition` (maps everything to `network`)                    |
| B2  | Embedded, local STT: whisper.cpp `whisper-server` with `ggml-large-v3-turbo`, language `cs`, behind `POST /api/speech/transcribe`                                                                        | Works offline, free, good Czech; mirrors the existing `speakd` TTS proxy pattern in `api/speech`                            |
| B3  | The API spawns `whisper-server` lazily on the first transcription when the binary and model exist; `WHISPER_URL` overrides to an external daemon. Missing → `GET /speech/status` reports STT unavailable | No daemon for the operator to babysit; the UI can hide the mic instead of failing                                           |
| B4  | Web: record with `MediaRecorder`, transcribe on stop (no live interim text). Used when the backend reports STT available; Web Speech stays as fallback in a plain browser                                | Smallest change that works in Electron; streaming partials are a later nicety                                               |
| B5  | Audio conversion via `ffmpeg` (`whisper-server --convert`)                                                                                                                                               | MediaRecorder yields webm/opus or mp4/aac depending on the engine; whisper wants WAV                                        |
| B6  | Desktop: add `NSMicrophoneUsageDescription` and a permission handler that grants `media` only to the app's own origin                                                                                    | Required for any mic use in the packaged app                                                                                |
| B7  | Mic also on the new-task input, not only the chat dock                                                                                                                                                   | The operator works from the dashboard                                                                                       |
| B8  | Hex / Wispr Flow are not integrated. Hex remains a zero-code system-wide alternative the operator can install themself (its brew tap needs `brew trust`)                                                 | System-wide tools paste into any input without code; trusting a third-party tap is the operator's call                      |
